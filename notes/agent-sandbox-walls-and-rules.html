Agent 沙箱缺的那半块拼图：Kata 挡得住内核漏洞，挡不住数据外泄

架构探秘　·　2026-11-10　·　摘要约 1101 字　·　阅读原文 ↗

沙箱有两半：墙管代码逃不逃得出去，规矩管代码能把什么送出去。只砌一半，另一半的威胁就没人管。

核心要点

  • Red Hat 实验（2026-07，OpenShift 4.21）：三个同镜像、同 Agent（OpenCode）、同模型端点的 Pod，各挨两次攻击。
  • 仅 Kata：被提示注入诱导，把整份环境变量 POST 给攻击者。
  • 仅 OpenShell：拦住外泄，但被 CVE-2026-31431 跨容器逃逸。
  • 两层叠加：两关全过。
  • CVE-2026-31431（Copy Fail）：Linux 内核 AF_ALG 接口，给无特权进程页缓存写入原语，每次 4 字节，利用脚本仅 732 字节；2017 年以来内核均受影响，2026-05 进入 CISA KEV。Kata 因 virtiofs 不暴露宿主页缓存而挡住。
  • OpenShell 的四个设计：① 执法者在 Agent 之外（Gateway + Supervisor + Sandbox，Agent 不需要知道自己被监视）；② 出站策略精确到程序/方法/路径（YAML → OPA/Rego，热加载）；③ 真实凭证不进沙箱（Agent 只拿占位符，发往授权端点才替换）；④ 权限变更需人工审批，policy prover 用形式化逻辑校验边界（对抗实验中前沿 Agent 花两小时试图说服 AI 审核者放权，失败）。
  • 规矩的边界（Lasso Security，2026-04）：默认策略放行 gh/git 访问 GitHub，攻击者借用被放行的通道——恶意仓库把令牌用表情符号编码绕过扫描，运行时还原后开 PR 带出密钥；npm 包注册定时任务做持久化，先探测哪些「域名×程序」被放行再周期性外传。策略管得住数据往哪去，评估不了意图。
  • 落地三档：本机试验（OpenShell + Docker/Podman，先拒绝再放行）；团队 K8s（Kata RuntimeClass + CNI 强制 NetworkPolicy，审批接 Slack）；多租户/强监管（独立工作区 + policy prover，评估 BlueField-4 上的 Sentry 带外监控）。
  • 最小清单：出站默认拒绝、凭证通过 provider 注入、文件与进程策略创建时定死、新增权限人工审批、宿主内核及时打补丁。

值得记住的结论

注意结论来自厂商 PoC（Red Hat 卖的就是 Kata 沙箱），别当胜负榜读。真正可迁移的是结构性结论：两类威胁需要两类机制，而且「被放行的通道」永远是最短的那条攻击路径。
