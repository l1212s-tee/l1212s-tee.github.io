端侧 AI Agent 的安全护栏：执行点、语义可见性与审计成本

USTCSweet　·　2026-11-10　·　摘要约 1264 字　·　阅读原文 ↗

把「内生还是外建」的路线之争，还原成三个可验证的问题：谁持有执行点、谁看得见语义、谁承担审计成本。

核心要点

  • 执行点：工具调用被允许前、文件写入前、网络请求发出前的强制位置。没有执行点的护栏只是观测或建议系统。执行点分散在内核、容器运行时、浏览器扩展、终端代理、身份代理，同一文件访问在不同智能体里走完全不同的路径。
  • 内生是概率防线：OpenAI 的 instruction hierarchy 按 system/developer/user/tool 四层训练优先级，对未见攻击类型鲁棒性提升、标准能力退化很小——但它是降低期望值，无法对单次请求给确定性保证。缺口在于没人给出失效概率的量级。
  • 外建提供确定性边界：其确定性不来自检测模型多聪明，而来自企业策略上下文——模型训练阶段拿不到的信息。合理定位是对一组明确列举的高风险执行路径做确定性控制，并产生可与内生日志关联的审计事件。
  • 供应链三类分开管：代码依赖（签名、版本锁定、受控仓库，已标准化）；模型与数据资产（来源证明、数据血缘、训练记录，普遍薄弱）；运行时外部服务与 MCP 插件（身份认证、权限约束、行为审计，多数企业无固定动作）。模型权重后门与训练数据投毒无法用签名解决。
  • 语义可见性取决于钩子：参考微软 Defender for Endpoint 的 AI agent runtime protection——用户提示、工具调用前、工具响应后三个检查点，Audit/Block 双模式；CrowdStrike 走行为建模路线（覆盖未知手法，但与语义检测互补）。旁路观测（命令行、流量元数据、文件日志）撑不起语义层。
  • 一个外部预判：Gartner 认为到 2029 年，针对智能体的成功攻击中过半会利用访问控制问题，直接/间接提示注入是投递机制。
  • 沙箱不是产品专属：操作系统本来就持有执行点（Claude Code 在 macOS 用 Seatbelt、Linux/WSL2 用 bubblewrap）。
  • 同构场景算总账：平台原生（Bedrock AgentCore 调 Guardrails、Google Model Armor 内联 Agent Gateway/Runtime/MCP）＋ OS 强制 ＋ 条件访问，往往比外建便宜。外建价值与「智能体生态异构度」正相关，与攻击面大小无关。
  • 采购三问：① 要覆盖的智能体是否跨五家以上厂商；② 框架是否暴露可用钩子（要求现场做一次带工具调用的注入阻断测试，只看仪表盘截图就是失败信号）；③ 智能体身份是否已纳入企业身份目录（Entra Agent ID / SPIFFE-SPIRE），否则只能在用户级做粗放控制。

值得记住的结论

判据顺序应该是：先补身份，再要钩子，最后才谈检测算法。算法精度在采购阶段根本验证不了，钩子清单和身份目录却是架构里固定的东西。
